# ALX Oracle — v1.1

Changelog и рекомендации по итогам эволюции из монолитного `index.html` (v1.0) в модульную архитектуру.

## Что сделано

### Архитектура
- Один файл (~1080 строк) разделён на `index.html` + 4 CSS-файла + 7 JS ES6-модулей + `data/mixes.json`, как и требовалось:
  - `css/main.css` — фон, типографика, кнопки, счётчик, бренд
  - `css/orb.css` — сам шар-глобус (сфера, кольцо, экран, дым)
  - `css/animations.css` — все `@keyframes` в одном месте
  - `css/cards.css` — карточка микса, шторка избранного/истории, toast
  - `js/storage.js` — безопасная обёртка над `localStorage` (с фолбэком в память, если хранилище недоступно — приватный режим и т.п.)
  - `js/profile.js` — избранное, история, настройки; уже отдаёт `getTasteProfile()` как задел для будущей персонализации
  - `js/mixes.js` — единственная точка загрузки `data/mixes.json`, кэширует, не падает при сетевой ошибке
  - `js/oracle.js` — Oracle Engine: `oracleChooseMix(context)` + Personality Engine
  - `js/effects.js` — вращение глобуса, печать текста, дым, частицы
  - `js/ui.js` — вся отрисовка DOM (карточка, фразы, шторки, toast)
  - `js/app.js` — только оркестрация сцены и обработчики событий
- Никакого jQuery/React/Vue — чистый ES6 (`const`/`let`, стрелочные функции, модули, шаблонные строки).
- Ноль глобальных переменных вне модулей (каждый файл — свой scope).

### Oracle Engine
- `pickMix()` полностью упразднён. Теперь `oracleChooseMix(context = {})`:
  - уже принимает `context` и задокументирован под будущие `favoriteIds`, `history`, `mood`, `timeOfDay`, `season`, `weather`;
  - возвращает не просто микс, а `{ mix, phrase, phraseCategory }`.

### Personality Engine
- 110 уникальных фраз оракула (было бы 100 по ТЗ — сделал с запасом), разбиты на 6 категорий: Загадочные, Добрые, Шутливые, Уверенные, Редкие, Эпические.
- Редкие/Эпические выпадают заметно реже остальных (взвешенный выбор, не равномерный) — это и создаёт ощущение «предсказания», а не ровного рандома.
- Одна и та же фраза не повторяется два раза подряд.
- Слова «случайный», «random», «генератор» и т.п. нигде не используются в пользовательских текстах.

### UX-сценарий
Вместо мгновенного показа — сцена на ~2.7–3.2 сек (зависит от длины названия микса), полностью на `setTimeout`/`requestAnimationFrame`, без единого блокирующего `sleep`:

```
Нажатие/встряхивание
  → шар «начинает светиться» (усиление ореола) + разгон вращения
  → появляется дым (лёгкие поднимающиеся сгустки света внутри шара)
  → экран гаснет (смена подсветки)
  → появляется фраза оракула
  → короткая повторная смена подсветки
  → название микса печатается по буквам (с уважением к переносу строк)
  → карточка микса красиво выезжает снизу
  → шар плавно возвращается к спокойному вращению, дым рассеивается
```

### Данные (новая схема)
Было: `{ name, desc }` (просто строка вкусов).
Стало:
```json
{
  "id": "mix-001",
  "name": "Cherry Crime",
  "description": "Вишня — основа, меренга — тонкая подсветка сверху.",
  "recipe": [{ "flavor": "Вишня", "percent": 50 }, ...],
  "strength": 2, "freshness": 1, "sweetness": 1, "sourness": 1, "difficulty": 2,
  "popularity": 41,
  "brands": [],
  "season": "всесезонный",
  "mood": "универсальное",
  "rating": null,
  "favorites": 0,
  "author": "ALX Oracle"
}
```
Все 228 миксов мигрированы. **Важно и честно:** `strength/freshness/sweetness/sourness/difficulty/popularity/season/mood` — это эвристическая (по ключевым словам состава) первичная разметка, а не данные из реальных дегустаций или пользовательских оценок. Это нужно проговорить в продукте прозрачно (например, мелким текстом «оценка редакции») — либо заменить в v1.2 на реальные пользовательские рейтинги.

### Карточка микса
Полностью переделана: название, рейтинг (или эвристическая «популярность», если реальных оценок ещё нет — раньше здесь была потенциальная ошибка на `null.toFixed()`, теперь исправлено), описание, чипсы состава с процентами, «профиль вкуса» (5 шкал точками), автор, кнопка «Поделиться» (через `Telegram.WebApp.switchInlineQuery` → `navigator.share` → буфer обмена, в порядке приоритета) и кнопка ♡/♥ «Сохранить» — **уже с рабочей логикой**, не заглушка: сохраняет в `localStorage` через `profile.js`.

### Storage / Profile
- `favorites[]` и `history[]` реально работают (не просто подготовлены);
- добавлены кнопки «Избранное» и «История» (шторка снизу) — это уже сверх минимального ТЗ, но тестировать сохранение без интерфейса было бы бессмысленно;
- `settings` подготовлены (`hapticsEnabled` и т.п.) для будущего экрана настроек.

### Анимации
- Glow/blur/bloom у шара усилены на состоянии «раздумья» (`orb-wrap.thinking`);
- дым — новый эффект, отдельный CSS + JS-модуль;
- карточка и toast получили мягкий inout;
- везде уважается `prefers-reduced-motion`.

### Исправленные баги при миграции
1. `mix.rating.toFixed(1)` падал бы на `null` (реальных оценок ещё нет) — добавлен график fallback на эвристическую популярность.
2. В нескольких авто-сгенерированных описаниях были падежные ошибки («держится на шоколад» вместо «на шоколаде») — шаблоны переписаны так, чтобы работать только с именительным падежом, без склонений.

## v1.1.1 — фикс тайминга сцены раскрытия

**Баг:** экран (`.screen`) гаснет/загорается через CSS-переход длиной 0.8с, а JS в `app.js` ждал меньше этого времени. В результате фраза оракула успевала стать видимой лишь на ~150мс перед тем, как снова начать гаснуть — физически невозможно было прочитать.

**Исправлено:**
- Длительность CSS-перехода `.screen` синхронизирована с паузами в `app.js` (420мс в обоих местах) — JS больше не убегает вперёд собственной анимации.
- Фраза оракула теперь печатается по буквам той же функцией `typeText()`, что и название микса (раньше — просто fade целым блоком) — оба появления выглядят как один и тот же механизм, а не два разных.
- Время показа фразы — адаптивное (`max(380мс, длина_фразы × 8мс)`), а не фиксированное число: короткая фраза не «висит» зря, длинная не улетает раньше, чем её успели прочитать.
- Добавлена страховка на перенос строк для длинных фраз оракула (line-clamp), чтобы самая длинная фраза (64 символа) гарантированно помещалась в круглый экран.

Новый полный цикл «встряхнул → шар думает → фраза → микс → карточка» — около 4.3–4.6 сек в зависимости от длины конкретной фразы и названия микса.

## v1.2 — Stability Release

Никакого нового функционала — только устойчивость. Цель: одинаковое, предсказуемое поведение в браузере и в Telegram Mini App при любых внештатных условиях (медленное устройство, сворачивание приложения посреди анимации, двойной тап, повреждённый JSON).

### 1. Полноценная State Machine (`js/scene.js`)
Новый модуль `SceneController` — единственное место, которое имеет право менять сцену:
```
IDLE → PREPARING → THINKING → CHOOSING → REVEAL → RESULT → RESET → IDLE
```
`app.js` теперь не хранит булевых флагов вроде `busy` — вместо этого `scene.beginScene()` / `scene.transition()` / `scene.endScene()`. Ни `oracle.js`, ни `ui.js`, ни `effects.js` не решают сами, что показывать дальше.

### 2. Двойной запуск устранён на уровне архитектуры
`scene.beginScene()` — первая синхронная операция в `runScene()`, до единого `await`. Если сцена уже идёт (`state !== IDLE`) — возвращает `null`, и функция немедленно выходит. Не имеет значения, что стало триггером — click, touch, devicemotion или Telegram-событие: вторая сцена физически не может стартовать поверх первой. Отдельно защищена регистрация слушателя `devicemotion` от повторного навешивания.

**Проверено тестом:** `beginScene()` во время активной сцены гарантированно возвращает `null` (см. раздел «Тестирование» ниже).

### 3. Устранён реальный источник «повтора размышлений оракула»
Нашёл и исправил корневую причину, а не симптом: `typeText()` (посимвольная печать и фразы оракула, и названия микса) раньше ничем не останавливалась. Если бы сцена прерывалась (по таймауту, по ошибке, при сворачивании приложения) во время печати — старые `setTimeout`-цепочки печати продолжали бы молчаливо мутировать DOM в фоне, поверх уже новой сцены. Это и есть тот самый «повтор» — два независимых потока печати в одном элементе.

**Исправлено:** `typeText()` теперь принимает `AbortSignal`. При отмене сцены все её локальные таймеры немедленно очищаются, печать останавливается на середине и не пытается закончиться. `renderOraclePhrase()` и `renderOrbText()` в `ui.js` пробрасывают сигнал дальше.

**Проверено тестом:** после `abort()` посреди печати ни одна новая буква не появляется, `onDone` не вызывается (см. «Тестирование»).

### 4. Debug Mode
`?debug=1` в URL (сохраняется в `localStorage`, переживает перезагрузку) либо `ALXDebug.enable()` / `ALXDebug.disable()` из консоли. Включает в консоль:
```
[ALX Oracle] Scene -> THINKING
[ALX Oracle] Этап PREPARING занял 42мс
...
[ALX Oracle] Полная сцена заняла 4180мс
```

### 5. Защита от зависаний
Каждый этап обёрнут в `scene.guard(promise, 3000)`. Если этап не укладывается в 3 секунды — `AbortController.abort()`, сцена прерывается, в консоль летит понятная ошибка, приложение гарантированно возвращается в `IDLE` (не «зависает» на месте).

### 6. Гарантированное завершение через try/catch/finally
`runScene()` целиком обёрнута в `try { ... } catch (err) { ... } finally { ... }`. В `finally` — безусловно: остановка вращения к состоянию покоя, снятие класса `thinking`, очистка дыма, `scene.endScene()`. Независимо от того, где именно и почему упал этап.

### 7. Telegram Mini App совместимость
`tg.ready()` и `tg.expand()` обёрнуты в `try/catch` (раньше не были — недоступный API мог уронить инициализацию до того, как отработает остальной код). `HapticFeedback`, `setHeaderColor`, `DeviceMotionEvent.requestPermission` — везде уже были safe-fallback'и, теперь проверено ещё раз явно.

### 8–9. Таймеры и слушатели
- `wait()` теперь тоже принимает `signal` и отклоняется немедленно при отмене, а не «висит» до истечения полного времени.
- `typeText()` очищает все свои локальные `setTimeout` при `abort` — ноль накапливающихся таймеров.
- Постоянный `requestAnimationFrame`-цикл вращения глобуса (`effects.js`) — единственный «вечный» цикл в приложении, и это осознанное решение: это фоновая анимация самого шара, а не часть сцены, она сама себя не дублирует (каждый тик планирует ровно один следующий).
- `devicemotion` защищён от повторной регистрации отдельным флагом.

### 10. Загрузка миксов
`mixes.js` уже проверял пустой/повреждённый JSON и раньше — теперь `runScene()` явно `await`-ит `initMixes()` на этапе `PREPARING` (с тем же 3-секундным таймаутом) и проверяет `hasMixes()` **до** начала анимации. Если данных нет — сцена не запускается вообще, пользователь видит toast «Не удалось загрузить базу миксов», а не пустой красивый спектакль без результата.

### Тестирование
Реальные функциональные тесты (не только синтаксис), прогнаны через Node + jsdom:
- **15/15** тестов `SceneController`: базовые переходы, защита от двойного запуска, `guard()` с реальным таймаутом и реальной отменой, гарантированный возврат в `IDLE`.
- **5/5** тестов `typeText()` с `AbortSignal`: нормальная печать до конца, остановка на середине по `abort()`, отсутствие мутаций DOM после отмены, отказ стартовать при уже отменённом сигнале.

### Известные ограничения (Medium/Low, на заметку для code review)
- **Medium.** `guard()` оборачивает промис таймаутом, но сам исходный промис (например, `renderOraclePhrase`) при проигрыше гонки не отменяется явно самим `guard()` — отмена происходит косвенно, через `AbortController.abort()`, на который подписан `typeText()`. Это работает (см. тесты), но для полностью строгой архитектуры в v1.3 стоит явно передавать `signal` во все guard-вызовы, а не полагаться на то, что переданный промис сам умеет его слушать.
- **Low.** `SHAKE_THRESHOLD`/`SHAKE_COOLDOWN` — по-прежнему константы, не связанные со `SceneController`; если понадобится телеметрия по частоте встряхиваний — их стоит завести туда же.
- **Low.** Debug Mode логирует только в `console` — для реальной диагностики на проде (Telegram Android/iOS, где консоль не видна) в следующей версии имеет смысл присылать debug-лог в чат боту по кнопке «Сообщить об ошибке».

### Рекомендации для следующего релиза
1. Провести именно то ручное тестирование, которое указано в пункте 12 ТЗ (Chrome / GitHub Pages / Telegram Android / Telegram Desktop / по возможности iOS) — автоматические тесты выше покрывают логику, но не рендеринг и не реальные особенности WebView.
2. Устранить Medium-замечание выше (явная передача `signal` во все guard-вызовы).
3. Добавить кнопку «Сообщить об ошибке», которая в Debug Mode собирает последние 10 переходов сцены и отправляет боту — сильно ускорит диагностику реальных проблем на проде.

## v1.2.1 — Stability & Scene Rewrite

Ответ на критику предыдущего этапа: SceneController существовал, но `app.js` всё ещё сам управлял деталями сцены (DOM, таймеры, Telegram) — то есть архитектурная неоднозначность оставалась. В этой версии владение сценой перенесено полностью в `scene.js`, а `guard()`-обёртка вокруг `Promise.race` заменена на честную кооперативную отмену через `AbortSignal`.

### 1–2. Разделение ответственности: `app.js -> SceneController -> Oracle Engine -> UI Renderer -> Effects`
`app.js` теперь содержит только: инициализацию, подключение Telegram, регистрацию событий и один вызов `initScene()` + `requestOracle()`. Вся детальная последовательность сцены (какой этап за каким, сколько ждать, когда гасить экран) переехала в `scene.js`. `oracle.js`, `ui.js`, `effects.js` по-прежнему ничего не решают сами — они выполняют, что им сказали, и отчитываются через `Promise`.

### 3–4. Единственный вход, разделение scene lock / mix lock
Новая единственная точка входа — `requestOracle()` (экспортируется из `scene.js`). И click, и `devicemotion` вызывают только её. `scene lock` — это исключительно `state !== IDLE` внутри `scene.js` (никакого отдельного `busy`). `mix lock` (`locked` — закрепление показанного микса пользователем) остался в `app.js` и проверяется **до** входа в `requestOracle()`, полностью независимо от состояния сцены — как и требовалось.

### 5–6. Один основной механизм ввода
На шаре — только `click`. `touchstart`/`touchend`/`pointerdown` намеренно не добавлены поверх него, чтобы Telegram WebView не мог инициировать два независимых события на одно и то же нажатие.

### 7. Shake — дополнительный, не основной
Если `DeviceMotionEvent` недоступен или пользователь не дал разрешение — приложение полностью работает через тап по шару, без единого экрана с ошибкой.

### 8. Упрощённый Thinking Flow
Новый сценарий ровно такой, как в ТЗ:
```
USER ACTION → START → THINKING → ОДНА ФРАЗА ОРАКУЛА → REVEAL → RESULT → CLEANUP → IDLE
```
Каждый этап — отдельная функция с одним входом (аргументы + `signal`) и одним выходом (`Promise`): `stageThinking()`, `stagePhrase()`, `stageReveal()`, `stageResult()`.

### 9. Устранён повтор «размышлений» — на уровне гарантии, а не только тестом
`renderOraclePhrase()` вызывается **ровно один раз** за сцену — это сейчас структурно невозможно нарушить, потому что вся последовательность линейна и живёт в одной `async`-функции `requestOracle()`, а не размазана по нескольким независимым обработчикам. Перед печатью нового текста контейнер очищается (`replaceChildren()`), поэтому наложение старого/нового текста исключено.

### 10. Никаких `id` для динамического контента
Убрал последний оставшийся случай — `renderCard()` в `ui.js` использовал `id="favBtn"` / `id="shareBtn"` через `innerHTML` + `getElementById()`. Переписал на `document.createElement()` с прямыми ссылками на узлы. Теперь единственные статические `id` в приложении — те, что заданы один раз в `index.html` для постоянных элементов интерфейса (`orbWrap`, `screenContent`, `mixCard` и т.п.), а не для контента, который переcоздаётся каждую сцену.

### 11. `typeText()` — один механизм вместо трёх
Было: `setTimeout` + `requestAnimationFrame` + `AbortSignal` одновременно. Стало: чистый `async/await` + один `setTimeout`-based `sleep(ms, signal)`. Каждая итерация цикла по буквам сама проверяет `signal.aborted` и выбрасывает `AbortError`, если сцену отменили. Никакого `requestAnimationFrame` внутри печати текста больше нет.

### 12–13. `guard()` заменён на честную кооперативную отмену
Признал критику по существу: старый `scene.guard(promise, 3000)` был `Promise.race` — он прекращал *ожидание*, но не отменял саму операцию. Теперь у сцены **один** watchdog-таймер на весь этап (`withTimeout()`), который при срабатывании вызывает `controller.abort()` на общем `AbortSignal` сцены. А все долгие операции (`sleep()`, `typeText()`) сами слушают этот `signal` и реально останавливаются — это и есть настоящая, а не имитационная отмена. Таймаут используется исключительно как аварийный механизм, а не как основной способ управления временем.

### 14–16. Гарантия возврата в IDLE, шар никогда не остаётся в burst
`requestOracle()` целиком в `try/catch/finally`. `finally` вызывает `cleanupScene()` безусловно: `rotator.setIdle()`, снятие `.thinking`, снятие `.off` с экрана, очистка дыма — что бы ни случилось на любом из этапов, включая таймаут и любое исключение.

### 17. Глобус — один RAF-луп, гарантированно
`createGlobeRotator()` теперь имеет защиту: повторный вызов не создаёт второй `requestAnimationFrame`-цикл, а возвращает уже существующий инстанс с предупреждением в консоль. Слушатель `resize` регистрируется один раз при первом создании.

### 18. JS не зависит от CSS-событий
Приложение никогда не слушало `animationend`/`transitionend` — тайминги JS синхронизированы с длительностью CSS-перехода через общую константу (`FADE = 420`, задокументировано в обоих местах), а не через ожидание браузерных событий.

### 19–20. Одна фраза оракула, без промежуточных сообщений
Отдельного «состояния размышлений» с несколькими текстами никогда не было в текущей реализации (когда я впервые проверил это по свежему ТЗ — ложной тревоги не нашёл), но структура `stagePhrase()` теперь явно гарантирует: один вызов `renderOraclePhrase()`, одна фраза, полная тишина между этапами — без «Оракул размышляет…» → «Оракул думает…» → «Оракул решил…».

### 22–23. Загрузка миксов: READY-барьер и cache-busting
`requestOracle()` явно `await`-ит `initMixes()` на этапе `PREPARING`, до включения любой анимации. Если `hasMixes()` вернул `false` — сцена не запускается вообще, пользователь видит toast, шар не крутится «в пустоту». Убрал `cache: 'force-cache'` (GitHub Pages мог отдавать устаревший файл) → `cache: 'no-cache'` + версионирование `data/mixes.json?v=1.2.1`.

### 24–27. Telegram API и логирование ошибок
`tg.ready`/`tg.expand`/`setHeaderColor`/`HapticFeedback` — везде `typeof fn === 'function'` перед вызовом + `try/catch` с `console.warn` (не молчаливый catch: сообщение всегда пишется, просто не считается критической ошибкой). Ошибки бизнес-логики (провал этапа сцены, отсутствие данных) — через `console.error('[ALX ERROR]', { stage, error, time })`, ни одного пустого `catch (e) {}` для логики сцены.

## v1.2.1 — Stability & Scene Rewrite

Никакого нового функционала. Задача: `SceneController` должен стать **фактическим**, а не номинальным владельцем сцены, и вся цепочка событие → сцена → эффекты → DOM должна быть максимально простой и однозначной.

### 1. Какие файлы изменены
- `js/scene.js` — переписан полностью.
- `js/app.js` — переписан полностью (сильно упрощён).
- `js/effects.js` — `typeText()` переписан полностью.
- `js/ui.js` — рендер-функции переписаны (без `id` для динамического контента).
- `js/mixes.js` — добавлен независимый таймаут на загрузку.
- `CHANGELOG.md` — этот файл.
- Без изменений: `index.html`, `css/*`, `js/oracle.js`, `js/profile.js`, `js/storage.js`, `data/mixes.json`.

### 2. Что именно изменено

**Архитектура приведена к:** `app.js → SceneController → Oracle Engine → UI Renderer → Effects`.

- `app.js` теперь **только**: Telegram-бутстрап, DOM-ссылки, `initScene(...)` один раз, регистрация событий, вызов `requestOracle()`. Он больше не знает, что «сначала гаснет экран, потом печатается фраза» — эта последовательность целиком переехала в `scene.js`.
- `scene.js` — единственный файл, который решает, что происходит на экране и когда. `oracle.js`, `ui.js`, `effects.js` ничего не решают сами — только выполняют то, что им передали, и отчитываются `Promise`.
- Единственная точка входа — `requestOracle()`. И `click`, и `devicemotion` вызывают ровно её, никто не имеет прямого доступа к внутренностям сцены.

### 3. Какие старые механизмы удалены
- Булев флаг `busy` — управление сценой полностью на `state !== IDLE` (`isRunning()`).
- `id="op"`, `id="mn"`, `id="md"` для динамического контента — заменены на прямые ссылки на DOM-узлы, создаваемые через `createElement` и передаваемые по цепочке вызовов.
- Смешение `requestAnimationFrame` + `setTimeout` + `AbortSignal` в одной функции `typeText()` — оставлен один механизм: `async/await` поверх `setTimeout`.
- «Гонка» как единственная защита (`Promise.race` без явного понимания её границ применимости).

### 4. Какие новые механизмы добавлены
- `withTimeout()` — явно документированная, честная граница ответственности: для операций, которыми сцена владеет полностью (`wait()`, `typeText()`), используется настоящая проверка `signal.aborted` на каждой итерации — это **реальная** отмена. Для общего кэшируемого ресурса (`initMixes()`, который не должен убиваться конкретной сценой, — иначе одна нетерпеливая попытка сломает загрузку данных для всех последующих) `withTimeout` честно **абандонит ожидание** через `Promise.race`, не убивая саму операцию — с этим же ресурсом разбирается пункт ниже.
- В `mixes.js` — собственный, независимый от сцен таймаут (6 сек) на сам `fetch`, через свой `AbortController`. Это и есть настоящая причина, по которой раньше зависшая сеть могла заблокировать приложение навсегда (см. «Что нашли тесты» ниже).
- Единый `cleanupScene()` в `finally`.
- Debug-лог в формате `[ALX] START / PREPARING / THINKING / PHRASE / REVEAL / RESULT / CLEANUP / IDLE` + `Scene duration: XXXms`.
- `[ALX ERROR]` с `{ stage, error, time }` на любую ошибку бизнес-логики (не Telegram-опциональщину).

### 5. Как устранён двойной запуск
`requestOracle()` синхронно проверяет `isRunning()` (единственный источник правды — состояние сцены) первой же строкой, до единого `await`. Пять кликов подряд, клик и «встряхивание» одновременно — гарантированно 1 сцена. **Доказано тестом** (см. ниже, п.28 ТЗ).

### 6. Как устранён двойной текст
`renderOraclePhrase()`/`renderOrbText()` в `ui.js` вызываются `scene.js` ровно один раз за сцену — это гарантируется тем, что сама последовательность стадий линейна и не содержит циклов/повторных вызовов. Плюс: `typeText()` при отмене реально останавливается (не просто «перестаёт ожидаться»), поэтому даже если бы сцена прервалась на середине печати, старый текст не может «дописаться» поверх нового. **Доказано тестом**: `MutationObserver` считает создание `.oracle-phrase` за сцену — ровно 1.

### 7. Как предотвращается зависание
Каждый этап обёрнут в `withTimeout(fn, signal, label)` с лимитом 3 секунды. **Именно тестируя это, я нашёл настоящий баг** (см. следующий раздел) и исправил его — не просто предположил, что «раз таймер есть, значит защита работает».

### 8. Как работает Telegram fallback
`tg.ready`, `tg.expand`, `tg.setHeaderColor`, `HapticFeedback.impactOccurred`, `DeviceMotionEvent.requestPermission` — каждый вызов обёрнут в проверку `typeof ... === 'function'` + `try/catch`, с `console.warn` (не молчаливым `catch(e){}`) на случай недоступности. Ни один из них не блокирует старт приложения или сцену — Motion вообще необязателен, основной сценарий (тап по шару) работает без него.

## ⚠️ Что нашли тесты — реальный баг, а не воображаемый

Я специально написал тест, имитирующий **реально зависшую сеть** (`fetch`, который никогда не резолвится) — именно то, что просил проверить п.32 ТЗ.

**Первый прогон этого теста провалился.** `requestOracle()` не возвращался вообще — завис на неопределённое время, хотя `console.error` про таймаут в лог всё-таки писался.

**Причина:** `withTimeout()` в первой версии этого рефакторинга полагался на то, что `fn(signal)` сам отреагирует на `AbortController.abort()`. Но `initMixes()` внутри делал `await fetch(...)`, а `fetch()` **не получал `signal` вообще** — соответственно, вызов `controller.abort()` из watchdog'а ни на что не влиял: таймер честно сработал и залогировал ошибку, но сама функция `withTimeout` продолжала бесконечно ждать `await fn(signal)`, потому что `fn` физически не могла остановиться.

**Исправлено:**
1. `withTimeout()` теперь по-настоящему `Promise.race()`-ит этап против таймера — `requestOracle()` гарантированно продолжится через 3 сек, что бы ни делала конкретная операция.
2. `mixes.js` получил собственный независимый таймаут (6 сек) на сам `fetch` через свой `AbortController` — чтобы шар не остался в burst-режиме навсегда при реально мёртвой сети, и чтобы это не зависело от того, сколько раз и как быстро пользователь тыкал в шар.

**После исправления тест воспроизведён ещё раз с полностью заблокированной сетью — сцена корректно прерывается за ~3 секунды, состояние возвращается в `IDLE`.** Это прямое доказательство работоспособности пункта 5, 13, 14 и 16 ТЗ, а не просто их декларация.

## Известные ограничения и рекомендации для code review
- **Medium.** Тайминг стадии `CHOOSING` (печать фразы + пауза на прочтение + fade) для самых длинных фраз оракула (64 символа) занимает до ~2.2–2.4 сек из бюджета в 3 сек — запас есть, но он не огромный. На медленном устройстве или под нагрузкой это стоит держать в поле зрения; при необходимости можно поднять `STAGE_TIMEOUT` именно для этой стадии до 4с, не трогая остальные.
- **Low.** `FETCH_TIMEOUT` в `mixes.js` (6 сек) сейчас захардкожен и не связан с `STAGE_TIMEOUT` в `scene.js` (3 сек) — это осознанно (это разные по смыслу лимиты, см. объяснение выше), но стоит явно задокументировать это решение в коде для следующего разработчика, чтобы кто-то не «синхронизировал» их по ошибке.
- **Low.** Debug-лог по-прежнему уходит только в `console` — для диагностики на реальных Android/iOS устройствах (где консоль не видна) полезно было бы добавить кнопку «Сообщить об ошибке», отправляющую последние переходы сцены боту.

## v1.2.2 — Final Stability Patch

Никакого нового функционала. Новых файлов не создано — вся правка внутри существующих `scene.js`, `effects.js`, `oracle.js`.

### 1. Список изменённых файлов
- `js/scene.js` — per-stage watchdog вместо единого лимита.
- `js/effects.js` — `typeText()`: защита от повторного запуска на элементе, debug-логи.
- `js/oracle.js` — 5 фраз про «размышления/сомнения» заменены на атмосферные.
- `css/orb.css` — поправлен один комментарий (не влияет на код).
- `CHANGELOG.md` — этот раздел.

### 2. Конкретные изменения

**Разделены операционный watchdog и визуальные тайминги (п.1 ТЗ).** Раньше был один `STAGE_TIMEOUT = 3000` на все этапы — этого хватало впритык для самых длинных фраз оракула (см. риск, отмеченный в v1.2.1). Теперь у каждого этапа свой лимит, честно documented как "аварийный fallback, а не расписание анимации":
```
PREPARING — 8000мс
THINKING  — 5000мс
CHOOSING  — 8000мс
REVEAL    — 8000мс
RESULT    — 5000мс
```
Реальная визуальная сцена по-прежнему занимает ~4–4.5 сек — лимиты в 2 раза больше самого длинного реального этапа, что и требовалось («реальный допустимый предел с запасом»).

**`typeText()` (п.4 ТЗ):**
- добавлен `WeakSet` активных элементов — повторный вызов на том же, ещё печатающемся элементе, теперь **не создаёт второй параллельный поток**, а логирует предупреждение и ничего не делает;
- добавлены debug-логи `TYPE START` / `TYPE COMPLETE` / `TYPE ABORT` (видны при `?debug=1`);
- уже было и подтверждено тестом снова: после `Abort` — ни одного изменения DOM, DOM не трогается после завершения сцены.

**Убраны все фразы про «размышления» (п.3 ТЗ).** Было 5 фраз с формулировками, создающими ощущение ожидания («Оракул подумал…», «Шар потратил… секунду раздумий», «минуту сомневался» и т.п.) — заменены на атмосферные, без апелляции к процессу мышления: «Свет внутри сферы выбрал именно тебя», «Дым сложился в узор — вот и весь выбор», «Искра внутри шара вспыхнула чуть ярче обычного» и др. Проверено скриптом: 111 фраз, все уникальны, ни одна не содержит «подумал/размышля/сомнева/раздум».

### 3. Какие проблемы найдены
Отдельных новых багов в этом патче не найдено — все три пункта (watchdog, typeText, фразы) были точечными правками без побочных эффектов. Полный набор тестов после правок остаётся зелёным (см. ниже), включая ранее найденный и исправленный в v1.2.1 баг с зависшей сетью — перепроверен уже под новым лимитом 8000мс, работает корректно.

### 4-5. Какие тесты выполнены и их результат

**Важно и честно, как в прошлый раз: всё ниже — симуляция в Node + jsdom, а НЕ реальный Chrome и НЕ реальный Telegram.** У меня в этой рабочей среде нет браузера и нет Telegram-клиента — я не могу физически провести 30 запусков в Chrome и 30 в Telegram, которые требует п.6-7 ТЗ. Ниже — то, что я реально могу и должен был проверить сам, плюс чёткая инструкция, что нужно проверить вам.

**`typeText()` — 9/9 тестов** (было 7, добавлено 2 под п.4 ТЗ):
- обычная печать, отмена, `signal` уже отменён при вызове — как раньше;
- **новое:** повторный вызов на печатающемся элементе → предупреждение, не второй поток;
- **новое:** после завершения элемент снова доступен для нового текста.

**`requestOracle()`, полный сценарий — 12/12 тестов:**
- **п.5 ТЗ, лично проверено по debug-логу**: `START → PREPARING → THINKING → CHOOSING → PHRASE → REVEAL → RESULT → CLEANUP → RESET → IDLE` — точно такая последовательность, без пропусков и повторов (сравнил список фактически залогированных переходов с ожидаемым списком строка в строку, не «на глаз»);
- 10 быстрых нажатий подряд → 1 сцена;
- клик + «shake» одновременно (3 показательных прогона) → 1 сцена на попытку;
- сцена штатно стартует после паузы простоя (аналог сворачивания/возврата — тайминги и `requestAnimationFrame` не ломаются и не накапливаются);
- mix-lock не путается со scene-lock;
- шар не остаётся в burst-режиме.

**Реально зависшая сеть — 3/3 теста:** сцена прерывается ровно по новому лимиту `PREPARING` (8000мс, замерено — 8004мс), не по старому 3000мс и не бесконечно.

**Итого: 24/24 автоматических теста пройдено.**

### Что я не проверял и прямо об этом говорю (п.6-7 ТЗ)
```
Chrome, 30 запусков:              НЕ ВЫПОЛНЕНО (нет браузера в этой среде)
Telegram Android, 30 запусков:    НЕ ВЫПОЛНЕНО (нет Telegram-клиента)
Telegram Desktop, 30 запусков:    НЕ ВЫПОЛНЕНО
Telegram iOS:                     НЕ ВЫПОЛНЕНО
```
Это не «PASS с оговоркой» — это честное «не проверено мной». Указывать здесь `30/30 PASS`, не выполнив тест, было бы прямой ложью, а не отчётом.

### Как быстро провести эту проверку самостоятельно
1. Откройте сайт с `?debug=1` в конце ссылки.
2. Откройте консоль (на десктопе — сразу; в Telegram Android/iOS консоль недоступна, но фиксируйте на глаз: белый экран, зависший шар, отсутствие карточки — это и есть FAIL).
3. Каждый тап — это одна строка `Scene duration: XXXms` без единого `[ALX ERROR]` между `START` и `IDLE` = **PASS**. Любой `[ALX ERROR]` или шар, оставшийся в вечном вращении = **FAIL**.
4. 10 быстрых нажатий подряд → в консоли должен появиться ровно один блок `START…IDLE`, а не десять.
5. Тап → сразу свернуть Telegram → подождать 5-10 сек → вернуться → проверить, что шар не завис (если завис — при следующем тапе `isRunning()` должен сам восстановиться максимум через 5-8 сек по новому watchdog, не позже).
